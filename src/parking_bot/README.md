# parking_bot

2026년 대회 차량 규격 이미지와 후진 주차장 치수 이미지를 반영한 ROS 2 Humble + Gazebo Fortress
LiDAR 기반 후진주차 시뮬레이션 패키지입니다. 실제 로봇은 자동차식 전륜 조향이 아니라
**제자리 회전이 되는 차동구동(differential drive) AMR**입니다.

## 실제 확인된 환경

- ROS 2 **Humble**
- Gazebo **Fortress** (`ign gazebo --version` → 6.18.0, `ignition-gazebo6` 계열)
- 월드/URDF의 모든 시스템 플러그인 filename/name은 Fortress 체계인 `ignition-gazebo-*` /
  `ignition::gazebo::systems::*`
- WSL2 + WSLg, GPU는 NVIDIA RTX 3050(노트북)

## 빌드/실행

```bash
cd ~/parking/ros2_ws
colcon build --symlink-install
source install/setup.bash
ros2 launch parking_bot sim.launch.py
```

`LIBGL_ALWAYS_SOFTWARE=1`을 손으로 넣을 필요 없습니다 — `launch/sim.launch.py`가 실행 시점에
자동으로 강제합니다(이유는 아래 "렌더링/GPU 관련 이슈" 참고).

## 렌더링/GPU 관련 이슈 (WSLg 환경 한정, 여러 번 실측 확인됨)

이 항목들은 로직 버그가 아니라 **이 WSL 환경의 그래픽 스택 문제**라 다른 환경에서는
해당 안 될 수 있습니다.

- **"Gazebo 창이 taskbar 아이콘만 뜨고 안 열림"**: Gazebo/코드 문제가 아니라 WSLg
  자체의 창 활성화(RDP RAIL) 버그였습니다 — 아무 X11 앱(`xterm` 등)도 똑같이 재현됨.
  `wsl --shutdown`으로는 안 고쳐지고, **Windows를 완전히 재부팅**해야 풀렸습니다
  (노트북이 절전모드에 들어갔다 나온 뒤 WSL의 GPU 가상화 채널(`dxgkrnl`)이 깨지는
  전형적인 증상 — `dmesg | grep dxgk`에서 `Ioctl failed` 반복이 보이면 이 케이스).
  재발하면 드라이버 재설치보다 **Windows 재부팅부터** 시도할 것.
- **`ogre2`(기본 렌더엔진) GL3Plus 크래시**: `gpu_lidar`/카메라 센서든 GUI 3D 뷰포트든,
  이 환경에서 GPU 가속(D3D12 통해서든 원래 하드웨어든)으로 렌더링하면
  `GenerateHwMipmaps`/`copyTo`에서 `Ogre::UnimplementedException`으로 100% abort합니다.
  **완전 소프트웨어 렌더링**(`LIBGL_ALWAYS_SOFTWARE=1`)에서는 안정적으로 동작 —
  `launch/sim.launch.py`가 이걸 강제합니다.
- **레거시 `ogre`(ogre1) 렌더엔진은 쓰지 말 것**: 크래시는 피하지만, `gpu_lidar` 센서가
  로봇 자기 몸체를 장애물로 오탐지하는(추정) 문제가 있어서 스폰 직후부터 최상위
  긴급회피가 계속 발동해 SEARCH가 아예 실행이 안 되고 장애물에 충돌했습니다
  (`worlds/parking_lot.sdf`의 `Sensors` 플러그인은 반드시 `ogre2` 유지).
- 트레이드오프: 위 조합(`ogre2` + 완전 소프트웨어 렌더링) 때문에 GUI가 다소 무거울 수
  있습니다(CPU 사용량 높음). GPU 가속을 다시 시도하려면 `ogre2`의 크래시부터 먼저
  해결해야 합니다.

## 컨트롤러 설계 (현재 버전)

실제 시나리오: 로봇은 주차구역 앞 차선(아일)을 따라 똑바로 직진하다가, 이미 주차된
차량(장애물) 사이의 빈자리를 찾으면 그 중앙에 멈추고, 개활지에서 제자리 회전으로
자세를 슬롯에 대해 수직으로 돌린 뒤, 직진으로 후진해 들어간다.

**라이다**: 차체 정중앙이 아니라 앞쪽(차체 중심에서 0.65m 앞)에 장착, 스캔 범위는
전방+좌우 **250도**(-125~+125도, 실제 규격 기준). 정후방 110도만 사각지대 — 그래서
후진 중 "뒤쪽 남은 거리"는 잴 수 없고, 대신 슬롯/차체 규격으로 미리 계산해둔 목표
정차 위치에 오도메트리로 도달했는지를 본다.

**상태머신**:

1. `SEARCH` (차선 직진): 직진 헤딩을 유지하며 로봇 왼쪽 정측면(90도) LiDAR 섹터
   하나로 "가깝다(장애물 옆)/멀다(빈 공간)"를 판정, `BEFORE_BOX1 -> AT_BOX1 ->
   IN_GAP` 순으로 추적하다가 다시 "가깝다"(box2)로 바뀌면 갭 진입/이탈 지점을
   기록하고 `RETURN_SCAN`으로 전환. 옆 장애물과 너무 가까워지면(0.75m 미만)
   멀어지는 쪽으로만 미세 조향(장애물 쪽으로는 절대 끌어당기지 않는 편측 보정)
   해서 직진 중 횡방향 드리프트를 막는다.
2. `RETURN_SCAN` (반대 방향 재측정): box2를 지나친 지점에서 살짝만 후진해
   "box2에서 벗어남"을 반대 방향에서 다시 잰다. SEARCH의 측정은 항상 전진(+x)
   중에만 이뤄져서 디바운스 지연이나 라이다가 모서리를 비스듬히 붙잡는 정도 같은
   "이동 방향에 따라 달라지는" 오차가 상쇄되지 않고 그대로 남는데, 같은 종류의
   전이(근접->이격)를 반대 방향에서 한 번 더 측정해 평균 내면 이 오차가 부호만
   반대로 걸려 상쇄된다 — box1까지 다시 갈 필요 없이 아주 짧은 후진(보통 2~3초)
   으로 끝난다. 자세한 유도는 `parking_controller.py`의 모듈 docstring 참고.
3. `BACK_TO_CENTER` (슬롯 중심 복귀): 재측정으로 계산한 슬롯 중심까지 헤딩 유지 +
   옆 장애물 안전거리 보정을 유지하며 이동한다. 라이다가 차체보다 앞서 있어 감지
   시점의 차체 위치가 목표보다 이미 지나쳤을 수도 못 미쳤을 수도 있으므로, 갈
   방향을 전환 시점에 계산한다.
4. `ROTATE_IN_PLACE` (제자리 회전): 반드시 장애물 사이로 들어가기 **전**(개활지)에
   목표 자세(-90도, 슬롯에 수직)까지 회전을 끝내야 한다 — 차체 대각선 회전반경
   (~0.8m)과 옆 장애물 사이 여유폭(1.2m)이 빠듯해서 중심이 안 맞으면 스칠 수 있다.
   실제로는 완전한 점 회전이 아니라 바퀴가 살짝 미끄러지며(스크럽) 회전 중 차체
   중심이 진행방향으로 약 5cm 밀리는 물리 현상이 있어, `BACK_TO_CENTER`의 목표
   지점을 미리 그만큼 반대로 당겨서 보정한다(회전 종료 시점 직접 계측으로 확인).
5. `STRAIGHT_REVERSE` (직진 후진): 회전이 끝나면 헤딩(-90도) 유지만으로 후진한다.
   좌/우 거리차 기반 실시간 중앙 정렬도 시도해봤지만, 좌우 라이다가 후진
   시작부터 동시에 잡히지 않아(한쪽은 초반부터, 반대쪽은 도착 직전에야) 대부분
   구간에서 보정이 꺼져있다가 막판에 급하게 작동해 오히려 결과가 나빠져서 뺐다.
   대신 회전 시작 위치 자체를 정확히 맞추는 쪽(RETURN_SCAN + 스크럽 보정)으로
   해결했다. 정지는 후방 감지가 아니라 "차체 중심이 목표 정차 위치(슬롯 중앙,
   오도메트리 기준)에 도달했는가"로 판단한다.
6. 최상위 긴급회피: 어느 상태든 전방위 12cm 이내로 장애물이 잡히면 최우선 발동,
   가장 가까운 장애물 반대쪽으로 회전하며 전진하는 단순 규칙.

자세(yaw)와 위치는 `/odom`(Gazebo DiffDrive 플러그인이 직접 발행)에서 받는다. odom
프레임은 스폰 지점을 원점으로 하므로, world/슬롯 좌표로 바꿀 때는 스폰 좌표(x=-2.0,
y=-0.6)를 더한다. 상태 전이의 1차 판단 기준은 항상 LiDAR, 오도메트리는 "얼마나
왔는지" 확인용 보조 수단.

## 검증 상태

- 실제 Gazebo GUI로 여러 번 눈으로 확인 + 오도메트리 궤적 정밀 분석(장애물과의
  실제 겹침 여부 계산, 4개 모서리별 여유 공간 계산)으로 **충돌 없이 SEARCH부터
  FINISHED까지 완주 + 정확한 정차 자세를 확인**했습니다.
- 최종 확인된 정밀도: 회전 종료 시점 요(yaw) 오차 **0도**(정확히 -90도), 최종
  좌우 중심 오차 **약 1cm**(슬롯 좌우 여유 공간이 각각 약 0.20m/0.22m로 거의
  대칭). 초기 버전(오차 ~6~7cm) 대비 여러 실측 기반 보정을 거쳐 개선됨 - 자세한
  경위는 `parking_controller.py`의 `RETURN_SCAN`/`ROTATE_SCRUB_DRIFT` 관련
  주석 참고.

## 장애물 배치 (`worlds/parking_lot.sdf`)

좌표계: 슬롯 입구 y=0, 안쪽 경계(정지선) y=1.6, 슬롯 폭 중심 x=0. 슬롯 자체
(1.0m x 1.6m)는 완전히 비어 있음(장애물 없음).

- `parked_box_left` / `parked_box_right`: 슬롯 좌/우 옆 칸에 이미 주차된 차량
  (0.5 x 0.9 x 0.6m, x=∓0.85, y=[0.1, 1.0]) — SEARCH/RETURN_SCAN의 편측 갭
  탐지 대상
- `parked_box_inner`: 슬롯 경계(y=1.6) **밖**, 보도블록에 붙은 장애물
  (0.9 x 0.5 x 0.6m, y=[1.8, 2.3]) — 정상 주차 동작과는 무관, 후방 안전 여유용

## 구성 요소

| 파일 | 내용 |
|---|---|
| `urdf/parking_bot.urdf.xacro` | 차량 모델 (차동구동, LiDAR 250도 FOV/카메라/GPS/IMU 탑재) |
| `worlds/parking_lot.sdf` | 1.0m x 1.6m 주차 슬롯 + 차선(0.1m) + 장애물 3개 |
| `parking_bot/parking_controller.py` | LiDAR 기반 후진주차 제어 노드 (상태머신 + 차동구동) |
| `launch/sim.launch.py` | Gazebo 실행 + 로봇 스폰 + 브리지 + 컨트롤러 통합 런치 |
| `config/ros_gz_bridge.yaml` | ROS2 <-> Gazebo 토픽 브리지 설정 |

## 반영한 규격 값

**차량 규격 이미지에서 그대로 가져온 값**
- 차체 길이/폭 범위(1200~1500mm / 600~900mm) 안에서 "헤네스 차량 예시"인 1400mm x 775mm 채택
- 구동: 차동구동(좌/우 바퀴 + 캐스터), 제자리 회전 가능
- 센서: LiDAR 1개(전방+좌우 250도), Camera 1개, GPS 1개 + 기타 센서로 IMU 1개 추가

**도면에 없어서 임의로 정한 값 (확인/조정 필요)**
- 좌/우 바퀴 간격(`wheel_separation`) 0.6m — 차체 폭에서 합리적으로 추정
- `parking_controller.py` 상단의 속도/거리 임계값 상수 — 실제 Gazebo 물리 특성에
  따라 재튜닝이 필요할 가능성이 있음(위 "검증 상태" 참고)
